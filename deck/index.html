One React library, six entry points, one theme

2:00 – 3:00. If you're new to it: Agrikit is CoBank's React component library. Everything with a Cb prefix comes from us. Everything else is plain MUI. @cobank-acb/shd-agrikit-ui-lib, MUI v7 and TypeScript, published to JFrog.

Two architecture points matter for app teams. First, it's layered: foundations, components, templates, patterns. CbAppShell and CbPage give you the whole product frame. Second, specialized features live in separate entry points (premium grid, Pro date range, PDF, notes, MFA), so you only pull those peer dependencies if you use them.

15:30 – 17:00. The part people underestimate is the review gate. The agent drafts a spec from this template first: what it will use, why, and what's in scope. It stops until you approve. That's how AI output stays reviewable.

Section 0 is the important one: is there already a Cb component, should we wrap it, or is this a real gap? Real gaps become issues for us. Layout primitives like Box, Stack and Grid stay allowed. The library repo adds code, security, test and web-performance reviewer agents.

TUTORIAL 01 · FROM IDEA TO A CONSISTENT APP

Tutorial: Build a Customer Portal screen with Agrikit

  1. Start from the app template. In /setup, choose Customer Portal or DAX to get the shared shell, routing and theme.
  2. Discover before you design. Use the Agrikit MCP tools list_components and get_component to find supported building blocks and their props.
  3. Describe the user outcome. For example: "Add a loans page with a CbPage, a CbCard summary and a CbDataGrid of loans."
  4. Review the spec before code. Confirm the component choices, scope and accessibility plan at the review gate.
  5. Verify the result. Check keyboard use, narrow layouts, light and dark themes, and imports from the Cb component set.

Make the request specific

Name the user task and the components the assistant discovered. Review its written plan before accepting an implementation.

TUTORIAL 02 · EXTEND AN EXISTING PRODUCT

Tutorial: Extend an approval workflow without rebuilding its UI

  1. Read the repository guidance. Check AGENTS.md and .github/instructions/ for local conventions, test commands and boundaries.
  2. Trace the existing flow. Follow the approval-package task through its screens, then use get_component to inspect the Agrikit components already in use.
  3. Extend, don't duplicate. Reuse the discovered components and layout patterns; for MUI-based screens, keep established imports and use Stack gap for spacing.
  4. Validate the change. Run validate_accessibility, test keyboard interaction and responsive states, then add a focused regression test.
  5. Close real gaps upstream. If no component fits, document the missing pattern and file an Agrikit issue instead of creating a one-off copy.

Keep the product's rules intact

Agrikit supplies consistent interface building blocks; the product team remains responsible for its approval and business logic.

25:00 – 26:00. Honest picture: there isn't one handoff process. Some teams are Figma-first, some prototype in the starter, a few already work component-first. All three ship, but they produce different amounts of rework, and new people can't tell which one to follow.

The pictures say it: drifting bars, one dot out of place, and parts that fit.

05 · Developer handoff · ideal state

One documented path, with Agrikit names from the start

  1. Product contextProduct + UX keep it current
  2. Name Cb partsIn stories and designs
  3. Discover & decideDirect, wrapper or custom
  4. ⛔ Spec reviewDev + design approve
  5. Build + storyFork or product repo
  6. Review & feed backGaps filed with Agrikit

26:00 – 27:30. The ideal isn't new tooling. It's using what we have, in this order. The biggest shift is step 2: requirements and designs name Cb components, so nobody has to interpret.

CbToolbar is the example, shipped last week. Its spec opens with the discovery decision: what it reuses, and each raw-MUI exception with a reason. It was approved before code, and the story on the right is what everyone reviewed.

On our side, library changes get tested against real consumer builds (the release-integration tarball check) before they ship. Keep ownership explicit: consumer teams validate app-specific behavior; Agrikit maintainers verify the release-integration build.
